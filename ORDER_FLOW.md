# Order Flow

This document traces the complete lifecycle of a single order from the browser to the matcher.

---

## Step 1 — Client sends a POST request

```
Browser
  POST /api/v1/order
  {
    "userId":    "user-uuid",
    "symbol":    "RIL_INR",
    "side":      "buy",
    "orderType": "limit",
    "price":     "250.00",
    "quantity":  "100",
    "orderId":   "client-generated-uuid"
  }
```

The `orderId` is generated by the frontend using `crypto.randomUUID()` so that
the same UUID is used in the DB, the Matcher, and the Execution Service.

---

## Step 2 — API Gateway validates and persists

```
api-gateway/src/routes/order.ts

1. Zod validates: symbol format, price > 0, quantity > 0, side enum
2. INSERT INTO "Order" (id, userId, symbol, side, orderType, price, quantity,
                         filledQty=0, remainingQty=quantity, status=OPEN)
3. → order is now durable even if the matcher crashes
```

---

## Step 3 — API Gateway forwards to Matcher Service

```
api-gateway/src/redisClient.ts

correlationId = randomUUID()          ← per-request reply channel
SUBSCRIBE(correlationId)              ← listen for matcher response
LPUSH "messages" {
  clientId: correlationId,
  message: { type: "CREATE_ORDER", data: {...} }
}
```

The gateway now blocks (with 7 s timeout) waiting for the matcher's response
on the `correlationId` channel.

---

## Step 4 — Matcher Service processes the order

```
matcher-service/src/index.ts          ← main loop: BRPOP "messages"
matcher-service/src/trade/Engine.ts   ← engine.process(message)

1. parseSymbol("RIL_INR") → baseAsset="RIL", quoteAsset="INR"
2. lockFunds(userId, price, qty)
   → deducts qty*price from wallet[INR].available
   → adds qty*price to wallet[INR].locked
3. orderbook.addOrder(order, { rest: true })  ← limit order rests on book
   → matchBuyAgainstAsks() — walks asks sorted by price ASC
   → if ask.price > order.price → stop (no match at this limit)
   → partial/full fill logic if asks exist within range
4. fills = [] (no match in this example)
5. order inserted into bids array at sorted position
```

---

## Step 5 — Matcher responds to API Gateway

```
RedisManager.sendToApiGateway(correlationId, {
  type: "ORDER_PLACED",
  payload: {
    orderId:       "client-generated-uuid",
    executedQty:   0,
    remainingQty:  100,
    restingOnBook: true,
    fills:         []
  }
})
→ PUBLISH(correlationId, ...)
```

---

## Step 6 — API Gateway resolves and responds to browser

```
The subscribe callback fires, timeout is cleared.
res.status(201).json(response.payload)
```

Browser receives:
```json
{
  "orderId":       "client-generated-uuid",
  "executedQty":   0,
  "remainingQty":  100,
  "restingOnBook": true,
  "fills":         []
}
```

---

## What happens when the order fills immediately?

If a matching ask already exists in the book:

```
fills = [{ matchId: "uuid", price: 248.50, qty: 100, ... }]
executedQty   = 100
remainingQty  = 0
restingOnBook = false
```

The matcher also:
- Updates in-memory wallets (both buyer and maker)
- Pushes `MATCH_CREATED` to Redis `db_processor` queue
- Pushes `ORDER_UPDATE` to Redis `db_processor` queue
- Publishes `trade@RIL_INR` to Redis (→ Realtime Service → Browser WS)
- Publishes `depth@RIL_INR` to Redis (→ Realtime Service → Browser WS)

---

## Order cancellation

```
DELETE /api/v1/order { orderId, symbol }
→ API Gateway → CANCEL_ORDER → Matcher
→ Matcher removes order from bids/asks array
→ Releases locked funds back to available
→ LPUSH db_processor ORDER_UPDATE{status:CANCELLED}
→ Execution Service UPDATE Order SET status=CANCELLED
```

---

## Supported order types

| Type | Behaviour |
|---|---|
| `limit` | Rests on the book at the specified price until matched or cancelled |
| `market` | Uses `effectivePrice = MAX_SAFE_INTEGER` (buy) or `0` (sell) to cross the entire book; unfilled remainder is discarded |
